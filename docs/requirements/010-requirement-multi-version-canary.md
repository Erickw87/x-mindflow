**Issue**: #10  
**作者**: xgopilot, ryan2255  
**日期**: 2025-10-24  
**状态**: 讨论中

---

## 📌 背景

本需求从 [Issue #3](https://github.com/LiusCraft/x-mindflow/issues/3) 拆分而来,专注讨论智能发布系统的**多版本并行与灰度发布**设计。

在企业级服务发布场景中,传统的"一刀切"发布方式存在较大风险。为了降低发布风险、提升发布成功率,需要支持渐进式的灰度发布策略,同时允许多个版本并行运行,实现平滑的版本迁移。

### 核心问题

1. **版本升级风险高**: 服务的 v1.1 还没有完全升级就需要升级 v1.2,传统方式无法支持
2. **流量切换粗暴**: 缺少流量维度的精细化控制,无法实现渐进式放量
3. **不兼容更新困难**: 新旧版本 API 不兼容时,无法共享流量,迁移困难

---

## 🎯 功能目标

支持同一服务多版本共存,通过**实例维度**和**流量维度**双重控制实现渐进式发布。

### 核心价值

- ✅ **降低发布风险**: 通过逐步放量,及时发现问题
- ✅ **提升发布灵活性**: 支持多版本并行,不阻塞后续版本发布
- ✅ **增强故障恢复能力**: 发现问题快速回滚,影响范围可控
- ✅ **支持不兼容更新**: 通过独立拓扑树实现物理隔离

---

## 📋 核心需求

### 需求 1: 多版本并行发布

**场景描述**:  
> 作为发布管理员,我希望在 v1.1 版本还在灰度过程中时,就可以开始部署 v1.2 版本,这样可以提升发布效率,不会因为前一个版本的缓慢推进而阻塞后续版本。

**功能点**:
- 同一服务最多支持 2-3 个版本同时运行
- 不同版本独立管理(实例数、配置、资源限制等)
- 支持版本间流量隔离(通过 LB 标签实现)
- 旧版本可以逐步下线,不影响新版本部署

**示例场景**:
```
时间线:
T1: v1.1 开始灰度 (10% 流量)
T2: v1.1 扩展到 30% 流量
T3: v1.2 开始部署 (v1.1 仍在 30%)
T4: v1.1 扩展到 100%,v1.2 开始灰度 10%
T5: v1.1 逐步下线,v1.2 扩展到 100%
```

**验收标准**:
- [ ] 支持同一服务 2-3 个版本同时运行在生产环境
- [ ] 每个版本有独立的实例池和配置
- [ ] 版本间流量互不干扰
- [ ] 可以独立控制每个版本的实例数和流量权重

---

### 需求 2: 灰度发布(渐进式放量)

**场景描述**:  
> 作为 SRE 工程师,我希望新版本先在小范围实例上运行,并逐步增加流量,这样可以在早期发现问题并及时止损,避免大面积故障。

#### 2.1 实例维度控制

**功能点**:
- 新版本实例逐步创建(如 10% → 30% → 50% → 100%)
- 旧版本实例逐步销毁(与新版本实例数成反比)
- 支持暂停点(需人工确认后继续)
- 支持自定义发布阶梯(步骤数、每步比例、暂停时间)

**实例分配规则**:
- 按百分比计算实例数(向上取整)
- 最小实例数保护(至少保留 1 个实例)
- 总实例数保持恒定(新增 + 旧有 = 总数)

**示例配置**:
```yaml
rollout_plan:
  steps:
    - instances: 10%   # 新版本 1 个,旧版本 9 个(假设总共 10 个)
      pause: manual    # 需人工确认
    - instances: 30%   # 新版本 3 个,旧版本 7 个
      pause: 5m        # 自动等待 5 分钟
    - instances: 50%   # 新版本 5 个,旧版本 5 个
      pause: 10m
    - instances: 100%  # 新版本 10 个,旧版本 0 个
```

**验收标准**:
- [ ] 支持自定义发布阶梯(至少 3 个步骤)
- [ ] 实例数按比例正确分配
- [ ] 支持手动暂停和自动暂停(基于时间)
- [ ] 实例创建/销毁操作能正确执行

#### 2.2 流量维度控制

**功能点**:
- LB 配置中调整新旧版本权重
- 支持按百分比分配流量
- 支持绝对实例数权重指定
- 流量权重与实例数可以不完全一致(支持手动覆盖)

**流量分配策略**:
- **默认策略**: 流量权重与实例数成正比(如 v1:v2 = 7:3 实例,则流量也是 70%:30%)
- **手动覆盖**: 允许固定小流量测试(如 10 个实例,v1:v2 = 9:1,但流量设置为 50%:50% 用于压测)

**示例配置**:
```yaml
traffic_control:
  strategy: proportional  # 默认:流量与实例数成比例
  override:               # 可选:手动覆盖
    v1: 50%
    v2: 50%
```

**验收标准**:
- [ ] LB 能根据配置正确分配流量
- [ ] 支持流量权重独立于实例数配置
- [ ] 流量分配误差在 ±5% 以内
- [ ] 支持会话保持(sticky session)

**关于 Q10 的决策**:  
**默认一致,允许手动覆盖**。流量分配默认跟随实例数比例,但支持手动覆盖用于特殊场景(如压测、固定小流量验证等)。

### 需求 3: 不兼容更新支持

**场景描述**:  
> 作为架构师,我希望在进行 API 不兼容的大版本升级时(如 v1 → v2),新旧版本能够物理隔离运行,避免流量串扰,待新版本完全验证后再统一切换入口。

**问题背景**:
- 新旧版本 API 不兼容,无法共享流量
- 需要独立的调用链路进行验证
- 验证完成后需要平滑切换入口

**解决方案**:  
通过 **LB 标签创建独立拓扑树**,实现新旧版本物理隔离。

**功能点**:
- 支持基于现有拓扑树克隆新树
- 新树中部署新版本服务
- 新旧树通过 LB 标签隔离
- 验证完成后切换入口,删除旧树

**实现流程**:
```
1. 克隆现有拓扑树(v1-tree → v2-tree)
2. 在 v2-tree 中部署新版本服务
3. 创建独立的测试入口指向 v2-tree
4. 逐步迁移流量到 v2-tree
5. 验证完成后:
   - 更新主入口指向 v2-tree
   - 标记 v1-tree 为待删除
   - 定时清理 v1-tree
```

**示例配置**:
```yaml
topology:
  name: "user-service-v2"
  cloned_from: "user-service-v1"
  isolation:
    enabled: true
    tag: "version:v2"
```

**验收标准**:
- [ ] 支持基于现有拓扑树克隆
- [ ] 新旧树流量完全隔离
- [ ] 支持独立入口访问新树
- [ ] 支持平滑切换主入口
- [ ] 旧树能正确清理

**共用中间节点处理(MVP)**:  
采用**方案 A(简单支持)**:不支持共用节点,所有树中流量段涉及的节点需拆分。如需共用,要求应用支持 Header 透传。

## 🚀 最小功能集(MVP)

### 1. 发布计划配置

**包含内容**:
- 发布步骤定义(阶段、实例比例、流量比例)
- 暂停点设置(手动/自动)
- 超时设置
- 回滚条件(MVP 阶段仅手动)

**配置示例**:
```yaml
deployment:
  service: "user-service"
  new_version: "v1.2.0"
  
rollout_plan:
  - step: 1
    instances_percent: 10
    traffic_percent: 10
    pause_type: manual
    timeout: 30m
  
  - step: 2
    instances_percent: 30
    traffic_percent: 30
    pause_type: auto
    pause_duration: 5m
    timeout: 30m
  
  - step: 3
    instances_percent: 100
    traffic_percent: 100
    pause_type: auto
    pause_duration: 10m
```

**验收标准**:
- [ ] 配置格式清晰,易于理解
- [ ] 支持至少 3 个发布步骤
- [ ] 支持手动暂停和自动暂停
- [ ] 支持超时保护

---

### 2. 实例数与流量权重联动控制

**功能点**:
- 根据配置自动计算实例数
- 自动更新 LB 权重配置
- 实时监控实例状态和流量分布
- 异常时能及时感知并告警

**实现要点**:
- 实例数计算:向上取整,最小值 1
- LB 权重更新:调用 LB 配置接口
- 状态监控:实例健康检查 + 流量监控

**验收标准**:
- [ ] 实例数按配置正确创建/销毁
- [ ] LB 权重同步更新
- [ ] 实例状态实时可见
- [ ] 流量分布符合预期(误差 ±5%)

---

### 3. 独立拓扑树创建

**功能点**:
- 基于 LB 配置克隆现有树
- 支持多树并存
- 流量标签隔离
- 树的生命周期管理

**验收标准**:
- [ ] 能基于现有树创建新树
- [ ] 新旧树流量完全隔离
- [ ] 支持查看所有拓扑树
- [ ] 支持删除不再使用的树

## 🔮 高级特性(后续迭代)

以下特性不在 MVP 范围内,但需要在设计时预留扩展性:

### 1. 金丝雀发布

- 先发布到特定机房/集群
- 验证通过后全量发布
- 支持基于地理位置的流量路由

### 2. A/B 测试

- 基于用户属性路由(如 user_id、地区、设备类型)
- 支持多变量实验
- 与数据分析平台集成

### 3. 流量镜像

- 复制生产流量到新版本
- 不影响用户请求(仅记录新版本响应)
- 用于验证新版本行为

### 4. 自动化回滚

- 基于监控指标自动触发回滚
- 支持自定义回滚条件
- 回滚决策日志记录

## ⚠️ 重要决策

### 决策 1: 蓝绿部署暂不实现

**背景**: Issue 中 Q9 提到是否支持蓝绿部署(一次性切换)

**决策**: MVP 阶段**不支持**蓝绿部署

**理由**:
- 当前聚焦金丝雀发布(渐进式灰度)
- 蓝绿部署可通过配置实现(`step=1, weight=100%`),但不作为独立功能
- 避免功能蔓延,保持 MVP 聚焦

**后续计划**: 根据实际需求再评估是否引入

**参考**: @xgopilot 在 PR #6 讨论中的反馈

---

### 决策 2: 流量与实例数关系

**背景**: Issue 中 Q10 提到流量占比是否与实例数占比一致

**决策**: **默认一致,允许手动覆盖**

**默认行为**:
- 流量分配与实例数成比例
- 例如: 10 个实例,v1:v2 = 7:3,则流量也是 70%:30%

**手动覆盖场景**:
- 压测:实例数 9:1,但流量设置为 50%:50%
- 固定小流量验证:实例数 5:5,但流量设置为 90%:10%

**理由**: 既满足常规场景(简化配置),又保留灵活性(支持特殊需求)

## 📐 设计原则

1. **逻辑与物理分离**: 用户配置逻辑概念(服务、版本、流量),系统负责物理实现
2. **面向状态的发布**: 声明式配置,系统自动驱动到目标状态
3. **以 LB 为核心的流量控制**: 拓扑即配置,LB 是流量控制的唯一入口
4. **最小化配置**: 提供合理默认值,用户只需配置关键参数
5. **去除 version 概念**: 全以 LB 链路表示,避免版本概念混淆

## 🔍 需要进一步讨论的问题

### 1. 发布计划的持久化

**问题**: 发布计划是每次手动配置,还是可以保存为模板?

**选项**:
- A: 每次手动配置(简单,但重复劳动多)
- B: 支持保存为模板,下次复用(更友好,但需要模板管理功能)

---

### 2. 发布过程中的异常处理

**问题**: 发布过程中出现异常(如实例启动失败、健康检查失败)如何处理?

**选项**:
- A: 自动回滚到上一步(安全,但可能误判)
- B: 暂停发布,等待人工决策(保守,但可能延误)
- C: 可配置(推荐)

---

### 3. 回滚操作的粒度

**问题**: 回滚是全部回滚,还是支持部分回滚?

**场景**:
- 全部回滚: v1.2 灰度到 30%,回滚后全部回到 v1.1
- 部分回滚: v1.2 灰度到 30%,回滚后退到 10%(回到上一步)

**建议**: MVP 支持全部回滚,部分回滚留给后续迭代

---

### 4. 多服务同时发布的协调

**问题**: 如果 A 服务依赖 B 服务,两者需要同时升级,如何协调?

**场景**:
- A 服务 v1.2 依赖 B 服务 v1.2
- A 和 B 需要同步灰度

**选项**:
- A: 不支持,用户手动协调(简单,但体验差)
- B: 支持发布编排,定义依赖关系(复杂,但体验好)

**建议**: MVP 不支持,留给后续迭代

## 🚫 非功能需求

### 性能要求

- **配置下发延迟**: ≤ 5 秒
- **实例创建时间**: ≤ 30 秒(取决于镜像大小)
- **LB 配置更新**: ≤ 3 秒
- **状态同步延迟**: ≤ 10 秒

### 可靠性

- **配置持久化**: 所有配置必须持久化到数据库
- **操作幂等性**: 所有操作支持重试,不会重复执行
- **状态一致性**: 系统崩溃后能恢复到正确状态

### 可观测性

- **操作日志**: 记录所有发布操作(谁、何时、做了什么)
- **状态变更历史**: 记录每次状态变更
- **审计追踪**: 支持审计和合规检查
